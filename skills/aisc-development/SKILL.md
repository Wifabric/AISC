# AISC 开发与整合

先从实际仓库确认工作树、分支、远端目标和当前提交，读取 [开发手册](../../DEVELOP_WIKI.md)、[活动计划](../../docs/plans/README.md) 和 [TODO](../../docs/todo.md)。用户本轮明确决定优先，引用已记录授权，避免再次询问同一问题。保护已有修改；已有实现和 PR 先核对，不重复开发。

计划使用 TODO 管需求、阶段计划管批次、PR_INTAKE 管审查集成证据。范围、顺序、负责人和验收条件写入现有条目，小修复不重写整套 PRD。只有未确认的新范围才留待决定；普通实现和已授权修正自主完成。用户暂时不可用时记录阻塞决定、建议和依赖部分，继续独立任务，不能把沉默视作批准。

## 按当前职责执行

主开发者使用 [PR intake](../../docs/workflows/pr-intake.md)：汇总 Issue、提议和全仓 PR，按已确认范围去重拆批，明确执行人、依赖和可观察结果。收集到 PR 不等于获准入版，PR 已合并也不等于用户验收。

任务执行者使用 [贡献者流程](../../docs/workflows/contributor-workflow.md)：从约定 develop 基线建功能分支，完成实现、相关测试和文档后提交 PR；说明实际 base/head、测试证据、未测项和后续安排。无需各自发布 Preview；必要自动化和真实数据面测试不能因统一 Preview 而跳过。

主开发者对版本整体负责。审查中的任务内小问题可直接修正并复验；跨任务契约或范围取舍按已有责任协调，不机械地反复退回作者。最终检查当前差异、精确 head 的适用 CI 和目标基线，按授权合入 develop；目标变化后复核受影响证据。个人开发可兼任这些角色，但只有自查时明确写自查，不称独立评审。

## 统一候选与交付

依当前阶段模式推进。小团队默认完成各批 PR/CI/集成后，由主开发者统一生成 Preview、检查实际集成版本并提供用户验收步骤；用户明确选择逐批验收时遵循该安排。界面验证、自动化、真实容器、安装验证和用户验收分别记 `PASS / FAIL / NOT RUN`，注明提交、环境和证据。依 [职责划分](../../docs/workflows/development-roles.md) 处理交接，角色不固定到某个具体人或编号前缀。

构建必须使用同一候选的前端、Rust、CLI 和容器 bundle；按 WIKI 的双轨版本和实际发布脚本准备产物，记录源码/二进制标识。不得用旧安装版或编译占位资源冒充新候选。失败先修复并重测受影响路径。

交付说明同时覆盖本版 Issue 修复、流程变化、验证结果和遗留项。依据实际权限和授权进行反馈回复、阶段收尾和发布；已有明确授权可沿用，尚未满足的产品决定、用户验收或 main/final 发布条件单列。完成候选准备不自动把 TODO 打勾、归档活动计划或关闭反馈。
