# 从主题反馈改进 skill

## 两种改动先分开

用户的时间、设备、风格和主题知识通常进入当前主题手册。若多个任务反复暴露澄清遗漏、记录断裂、做法不可执行、证据误判等流程问题，形成 skill_proposal 候选。严重且明确的通用缺陷可以先提出修复，不机械等待发生第二次；扩大为通用规则前仍需验证。

不把参与案例中的私人文件、姓名、账号、未公开成果或逐字对话复制进通用技能包。用抽象规则和经授权脱敏的案例测试。跨主题复用须说明哪些条件成立；不能让一个用户偏好自动影响其他用户。

## 候选最少应说明

- problem：具体在哪个任务失败，引用 interaction/trial/feedback 等记录。
- hypothesis：可能归因于目标、资料、规则、执行、验收还是现实因素；还有什么替代解释。
- scope：影响哪类任务，哪些场景不应受影响。
- proposed_change：最小改动，预期改变的可观察行为。
- validation：如何对比旧/新版本，正例、相近但不应触发的反例、恢复场景；成功与退回条件。
- status：proposed → tested → accepted/rejected；没有运行就不写 tested。

没有 skill 修改授权时，保存候选并向用户简述，不编辑安装文件。用户已明确授权本轮 skill 编辑时，不对每个可逆小修改重复要求批准。提案接受者和依据记录在 data 中；发布、外发、权限变更另依用户实际授权。

## 验证和版本

在隔离副本验证；记录旧/新 skill 版本、实际宿主/模型（可获知才填）、任务输入、产物、检查和限制。能提供独立新会话就使用，不能则注明自测。测试前确认写入范围；不把模拟任务送到真实外部账户。

同时看结果正确性和使用成本：漏掉约束了吗？新手能操作吗？多了无用提问吗？日志是否保真？能恢复吗？结构校验通过不等于行为正确。用未参与修改的新案例检查是否只适应一个例子；重要结论重复运行。

更新版本并保存上一版、具体差异和退回方法；重跑受影响场景及关键反例。自动描述“越来越好”没有意义，只有观察到的改善才能写入迭代结论。新版本无优势时保留旧版或缩小规则。

## 给 skill 维护者的反馈材料

从 journal 导出必要片段及关联产物，由用户确认隐私范围。保留原始反馈与后续归因的区别，并列已证实、推测和未知。导出仅发生在用户要求分享/维护时，普通主题任务不自动上传任何内容。
