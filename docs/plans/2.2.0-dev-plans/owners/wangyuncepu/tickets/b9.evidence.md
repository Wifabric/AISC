## 结论

标签/终端卡住时，运行时轮询会调用状态探针；一旦命中卡住判据，向共享 JSONL 时间线
（`<data root>/logs/aisc.log`，诊断包 `recent_log_events` 会带上）写入一条
`action="tab_stuck_probe"` 的结构化行，内含 tab/pane/engine/session/state、状态持续时长、
最后 PTY 活动、渲染队列深度，以及一行可直接复述的复现路径。同一卡住事件只记录一次，
恢复后再次卡住会重新记录。纯只读探针，不改变任何渲染/会话行为。

## 卡住判据（可调阈值集中在一处）

- `starting` 持续 ≥ `startingMs`（默认 20s）→ `starting_timeout`（PTY 一直没到 running）。
- `closing` 持续 ≥ `closingMs`（默认 15s）→ `closing_timeout`（关闭未终结）。
- 窗口可见、渲染队列连续两次探针**未排空**且 ≥ `queueStallMs`（默认 3s）→ `output_queue_stalled`（rAF/渲染消费停摆）。首次探针只作基线，隐藏窗口不计，避免误报。

不把「running 但暂时无输出」判为卡住（空闲 shell 不是 bug）。

## 复现路径怎么用

1. 从该行读取 `repro`：`workspace` / `runtime` / `tab` / `pane` / `engine` / `session` / `state` / `stateAge` / `lastActivity` / `queueDepth` 全部定位坐标。
2. `context.tabs` 给出当时**所有** pane 的同一组快照（不只卡住的那个），便于判断是单 pane 还是整机/渲染管线。
3. 诊断包导出（Doctor → `export_diagnostics` / `diagnostic_bundle`）包含 `aisc.log` 尾部，无需用户额外操作即可带走该记录。
4. 开发/手测时可直接在 devtools 调 `useRuntimeStore().probeStuckTabs()` 取完整报告，或 `logTabStuckProbeIfNeeded()` 手动落日志。
