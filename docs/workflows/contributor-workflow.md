# AISC 贡献者工作流 v1.0

适用于承担具体任务的开发人员，包括主开发人员亲自承接的任务。职责见 [开发职责](development-roles.md)，主开发人员接收 PR 的流程见 [PR intake](pr-intake.md)。本文接续 DEVELOP_WIKI 的阶段纪律，不另建版本计划或审批体系。

## 1. 找到自己的入口

| 当前情况 | 从哪里开始 |
| --- | --- |
| 承接已排期任务 | 读取对应 TODO、批次和现有 PR，确认承接，进入 §2 |
| 有新的想法或问题 | 提供来源、预期行为和影响，进入现有候选清单；范围确认后进入 §2 |
| 已有实现或 PR | 整理已实现范围、依赖和证据，直接按 §5 交付，由主开发人员核对范围、关联 TODO 和审查批次 |

已有成果不要求重做，但仍须审查和验证；未排期的贡献不自动进入当前版本。

## 2. 开始任务：确认交接，形成任务内方案

先读取集成目标的有效 DEVELOP_WIKI、活动计划和相关代码。核对任务是否已有人承接或已有 PR，查明能自行确认的事实，再处理真正影响方案的选择。

在现有批次条目中补齐以下信息即可，不要求新建一份完整 PRD：

```markdown
- 任务／批次／范围决定：<链接或编号及已有决定出处>
- 执行人／主审：<实际约定人员；未定写待安排>
- 本次做什么／不做什么：<范围与缺口>
- 工作基线／集成目标／依赖：<分支、提交、前置任务或 PR>
- 实现方案：<主要改动、共享接口及兼容影响>
- 验收条件／验证计划：<可观察结果、步骤、环境和阶段模式>
- 当前状态／下一步：<谁做什么；阻塞则说明所缺条件>
```

主开发人员提供或协调版本、批次和依赖；执行人确认承接并补任务方案。需要扩大范围、改变共享契约或影响其他批次时回到主开发人员协调，有用户保留决定权的事项继续按原规则处理。已有授权与决定直接引用，任务内普通实现选择自行完成。

## 3. 分支开发与进度同步

按 DEVELOP_WIKI §1.2 从约定基线建立独立工作分支；默认命名 `codex/<任务主题>`，已有明确命名约定时沿用。若计划明确采用父 PR 分支作为依赖基线，登记父 PR、实际 base 和最终集成目标；未经约定不能擅自改变基线。保留已有本地修改，不覆盖他人工作。

完成本任务涉及的代码、测试、接口说明和用户文档。修改 CLI、容器、依赖或打包资源时，依照手册对应章节处理消费链和校验，不只改表面入口。

在开始、提交审查、出现阻塞、完成修正、交接和完成时更新现有任务记录；涉及共同文件或接口的冲突及时同步。多人参与不意味着可以跳过前置批次或阶段验收条件；可并行范围由现有计划和主开发人员协调明确。

## 4. 提交前：自测与可审查材料

执行任务相关验证和当前阶段要求的本地门禁。涉及真实容器、Remote、安装／更新或 GUI 的变化，按约定提供相应验证；静态检查不能代替实际运行，CI 绿色也不代替用户验收。

每项证据说明提交、命令或操作步骤、环境、实际结果和日志位置。明确区分 `PASS / FAIL / NOT RUN`；无法完成的验证注明原因、影响及由谁补齐。适用门禁未满足时仍可交付草稿寻求协助，但不能将其标为已准备合入。

提交审查前，逐条将任务验收条件对应到验证结果和证据；可以在已有验证说明中直接列出，不必另建文件。没有覆盖的条件写 `NOT RUN`，不能用“自测若干项通过”代替完整覆盖。主审按相同条件复核；新增或重跑的检查说明对应哪个条件。

只提交必要的项目材料，检查 diff 和敏感信息。用合成或脱敏材料描述复现；已有关于测试、个人示例或日志上传范围的约定继续有效。若证据无法公开，应说明审查者怎样取得适用的验证依据，不能用无法查证的数量代替证据。

## 5. 提交 PR：把任务交给主审

在 PR 中直接填写以下信息，不重复制作多套账本：

```markdown
## 问题与结果
<具体触发条件、原行为、修改后的行为>

## 任务与范围
<TODO／批次／范围决定；已实现部分、未完成部分>

## 分支与依赖
<实际 base、head 提交、父 PR、最终集成目标；无依赖则注明>

## 验证
<逐条验收条件 → 命令或步骤、环境、对应提交、PASS／FAIL／NOT RUN、证据位置；未覆盖项及后续安排>

## 影响与交接
<兼容影响、迁移或回退注意事项；不适用则注明；下一步及所需协助>
```

主开发人员按 PR intake 核对范围、去重并安排主审。贡献者提交 PR 后仍负责约定的修正与交接；主审未指定或排期未决定时，保留真实等待状态，不能自行宣称审查通过。

## 6. 审查、修正、集成和完成

| 情况 | 贡献者执行 | 主开发人员／主审接续 |
| --- | --- | --- |
| 主审要求修正 | 逐项修正或说明异议依据，给出新提交及受影响验证 | 复审最新差异，明确继续修正、等待依赖或待合入 |
| 父 PR 已合入、目标分支变化或出现冲突 | 按协调结果更新分支，核对剩余 diff，重跑受影响验证 | 核对依赖、合入顺序及新提交证据；不沿用失效结论 |
| 已合入 | 配合本任务集成验证，补最终变更和限制 | 记录实际目标提交，组织本阶段验收和整体回归 |
| 集成或验收失败 | 按约定定位、修正并补证据 | 协调跨任务问题；任务保持未完成 |
| 任务验收条件满足 | 补齐任务结果、实际集成提交和后续事项 | 核对 TODO、批次与 PR 记录后收口；发布另按既有流程 |

主开发人员负责统筹和技术把关，用户／验收负责人作出其职责范围内的验收结论。贡献者可以按明确委托执行合并、回归或发布，但不能因有仓库权限就自行改变版本安排。

任务状态继续使用已有 TODO／批次记录；PR 状态使用 PR_INTAKE，不另创一套并行状态。PR 只实现部分需求时，只收口已完成部分，剩余任务有编号和负责人；不将整个需求提前打勾。

## 7. 阻塞、改派与退出

- **缺环境或无法验证**：记录缺少的条件、已验证范围和影响，请主开发人员协调资源或按原规则处理例外，不伪装通过。
- **需要扩大范围**：保留当前工作，说明新增需求与影响；通过既有范围流程后再实施依赖该决定的部分。
- **不能继续负责**：交出分支／PR、最后提交、已做与未做、复现与验证步骤、已知风险；主开发人员协调接手人并记录实际承接。未有人接手时保持待安排，不能把“已发消息”当作交接完成。
- **PR 关闭或贡献延期**：说明原因；主开发人员确认需求是取消、转期、换人还是由其他 PR 接续。关闭 PR 不自动关闭 TODO。

## 8. 双方交接演示

以下 DEMO 均为虚构，只验证文档路径，不代表实际分派、审查或合入。

| 步骤 | 执行者与动作 | 记录与下一位执行者 |
| --- | --- | --- |
| 1. 开题 | 主开发人员将已批准的“导出记录”排为 T1／b1；乙确认承接 | 批次记录目标、依赖和验收条件；乙开始任务方案 |
| 2. 实现 | 乙完成导出、自测和说明，提交 DEMO-A | PR 提供 diff、base/head、验证证据；主审开始审查 |
| 3. 退回 | 主审指出失败提示不清，写明复现步骤及期望 | PR 记待修正；乙负责处理 |
| 4. 修正 | 乙提供修正提交、逐项说明和复验结果 | 主审审查新 head；通过合入前要求才记待合入 |
| 5. 集成与验收 | 主开发人员按授权集成并组织验证，乙配合；用户按阶段模式验收 | 记录实际提交及验收结论；未通过时继续修正 |
| 6. 收口 | 乙补交付记录，主开发人员核对任务全部条件 | T1 完成；版本整体回归和发布由主开发人员继续统筹 |

若步骤 3 后乙无法继续，改走 §7 的明确交接；若 DEMO-A 在开题前已经写好，直接从 §1 的已有成果入口进入，不重新分派同一实现工作。

可用于启动任务的描述：

> 按 DEVELOP_WIKI 和贡献者工作流处理任务 <编号>。先读取范围、依赖、验收条件与已有 PR，引用已有决定，补任务内方案；在授权范围内完成实现、验证和交付材料。遇到跨任务影响或阻塞及时记录下一步，不把未测或待验收写成完成。
