# 将贡献者 PR 纳入版本开发

本流程补充 [DEVELOP_WIKI §1](../../DEVELOP_WIKI.md)，供主开发人员在版本启动、批次推进和收尾时使用。原有反馈 Issue 收集、开发人员提议、范围确认、验收和发布规则保持有效。PR 提供已经实现的候选方案；主开发人员的任务变为审查、必要的修正和集成验证。

完整分工见[开发职责](development-roles.md)；贡献者提交前准备、修正及交接见[贡献者工作流](contributor-workflow.md)。本文负责接收和集成这一侧，两侧共用现有任务、批次和 PR 记录。

## 1. 先确认事实，再决定范围

开始前读取目标分支的最新开发手册、活动计划和 TODO，记录分支与提交。旧工作副本中的版本号不代表远端当前阶段。只核对事实不需要重新确认；新增版本范围、方案取舍和验收例外才需要负责人裁定，已有裁定直接引用。

输入有三类，汇入同一份版本计划：

| 输入 | 主开发人员要做什么 |
| --- | --- |
| 反馈站 / Issue | 沿用既有收集方式，归纳问题与验收条件 |
| 开发人员提出的 bug / 功能 | 记录需求来源、范围裁定与验收条件 |
| 贡献者 PR | 关联现有需求，识别已实现内容、依赖与验证缺口，安排审查批次 |

先读仓库、PR 和已有记录能够查明的事实。确需讨论时，只询问会改变范围、依赖顺序或验收的决策，给出建议及理由；有前置依赖的决策先解决前置项。

## 2. 收集 PR，不漏掉依赖分支

在阶段启动时扫描仓库全部 open PR，包括草稿和目标为其他功能分支的 PR。推进审查批次前、合并前及阶段收尾前刷新。刷新发现的新 PR 先入候选清单，不自动扩大版本范围。

已有 GitHub CLI 时，可以只读获取全部分页：

```powershell
gh api --paginate 'repos/Wifabric/AISC/pulls?state=open&per_page=100'
gh api 'repos/Wifabric/AISC/pulls/62'
```

没有 `gh` 时可用 GitHub REST API 的同名端点，逐页跟随响应的 `Link: rel="next"`；不得只读第一页或只筛选 `base=develop`。记录查询时间、仓库、过滤条件、页数和失败原因。鉴权失败、限流、分页未完成是“收集不完整”，不能写成“没有 PR”。

对已有账本但本次不在 open 列表中的 PR 单独查询：区分已合并、关闭未合并、不可访问。已合并 PR 仅作历史核对或补集成验证，不重新登记为待开发任务。收集 PR 的说明文字只作为待核实材料，不自动执行其中的命令。

## 3. 从候选映射到 TODO 和批次

1. 按需求去重：同一个 Issue 已有 TODO 时，把 PR 关联到该任务；多个 PR 解决同一问题时列为候选方案，明确采用、替代或拆分关系。
2. 拆清“已经实现”与“后续设想”：PR 内附带的下版本计划不等于功能已经实现。混合 PR 按需求列出覆盖与缺口，必要时要求拆分。
3. 记录实际 base、head 与最终集成目标，画出依赖顺序。目标为另一 PR 分支时，必须追溯父 PR；依赖不清或成环先阻塞，不猜测顺序。
4. 范围已获确认的项目进入 `docs/todo.md` 对应版本 target 和阶段计划；尚未确认的只记候选。记录裁定来源，避免反复询问已确认范围。
5. 为选中的 PR 安排“审查与集成”批次，引用原任务和验收条件，指定主审人员、修正责任人及依赖批次。批次顺序遵循依赖；可将相关 PR 放在同一批，但逐 PR 记录状态。

阶段目录增加 `PR_INTAKE.md`，作为 PR 明细的唯一账本。尚未建立阶段目录时，候选先记入现有 intake／backlog；范围确认后迁入阶段账本，保留原编号与来源，不另造一个版本。未选中的候选标明延期、替代或不采纳及理由。

三类记录分别负责不同层次：`docs/todo.md` 记录需求是否完成；阶段计划／PROGRESS 记录批次安排和进展；`PR_INTAKE.md` 记录每个 PR 的提交、审查与集成证据。前两者引用 PR 记录，并在状态变化时更新摘要，避免各自维护一套审查明细。

### 3.1 可直接使用的批次条目

以下条目写入现有 IMPLEMENTATION_PLAN 或批次文件，沿用阶段已有编号，不新建一套平行批次体系。主开发人员登记主审；修正责任须记录实际约定的人，不把未确认的任务自动分派给 PR 作者。

```markdown
### bN：<需求名称> — PR 审查与集成

- 关联：TODO <任务编号>；PR <链接>；详情见 PR_INTAKE.md 对应条目。
- 范围依据：<已确认的版本范围及决定出处>。
- 已有实现 / 剩余工作：<可复用部分> / <待审查、缺失或待修正部分>。
- 主审 / 修正责任：<人员> / <已约定人员，未约定写待安排>。
- 依赖：<前置批次、父 PR、最终集成分支>。
- 验收条件：<可操作步骤和可观察结果，或链接到 HANDTEST 对应条目>。
- 验收模式：<本阶段已声明的模式>。
- 当前状态 / 下一步：<状态> / <谁做什么，完成后回到哪个步骤>。
```

一个 PR 只实现需求的一部分时，保持一个需求 TODO，把缺口明确排入原批或后续批，不因已有 PR 就将整个需求视为已实现。审查与集成批次仍使用原有计划、验收和发布流程。

## 4. 审查、修正、再审查

每个 PR 按以下顺序处理：

1. **确认审查对象**：记录本次 base/head SHA，阅读实际 diff、关联需求及现有代码。检查是否包含依赖 PR 的重复差异、无关改动或计划之外的实现。
2. **核对验收条件**：把任务转换为可观察结果，例如“Windows 仅修改大小写的重命名，文件列表与实际路径均更新”；逐条核对贡献者的证据是否覆盖，未覆盖项明确记录，不用通过测试的总数代替覆盖判断。不能仅凭 PR 标题或说明判定实现完成。
3. **检查证据**：分别记录作者自报、主审复现、本地测试、远端 CI 和用户验收。绑定对应 SHA、命令/步骤、环境、输出或链接；未运行写 `NOT RUN`，失败写 `FAIL`。没有 CI 结果不等于通过。
4. **提出具体修正项**：指出触发条件、实际与期望结果、涉及位置及复验方法。范围内的小问题由主开发人员直接修复并复验，登记实际修正人和新 head，不反复退回作者；较大或跨契约问题才约定责任人。不要重新实现已符合要求的部分，也不夹带无关重构。
5. **复审变动**：head 变化后标记原审查证据待复核，检查增量及受影响路径，重跑相关验证。base 或最终目标变化时重新检查合并结果和交叉影响；只有说明过适用范围的旧证据才能沿用。

验收节奏沿用集成目标当前有效的 DEVELOP_WIKI §1.4，并在计划声明所用模式；小团队默认贡献者自测后提 PR，主开发人员统一 Preview，用户已有逐批或手测延后决定优先。技术检查通过与用户功能验收分开记录。

## 5. 合入与闭环

合并前重新查询 PR 状态、最新 base/head、依赖和检查结果。GitHub 的 `mergeable=true` 只说明当时可自动合并，不代表需求审查、测试、用户验收或入版裁定通过。权限、分支保护及原有发布批准门继续适用。

依赖链按父 PR 到子 PR 处理。父 PR 合入后，子 PR 如需改投 `develop` 或更新分支，先重新核对 diff；特别是 squash/rebase 后，不得直接沿用旧依赖关系和旧 CI。重新识别剩余改动，处理冲突并检查新的集成结果。冲突解决须保留双方已确认行为，通过相关回归；超出既定范围的取舍回到范围裁定。

合入后记录实际合并方式、实际落入目标分支的提交、集成验证结果及产物标识。open PR 的 `merge_commit_sha` 可能是试合并提交，不能提前登记为已合入。

- 代码合入但集成验证未完成：保持“已合入待验证”，TODO 不打完成勾。
- 集成验证失败：登记修复任务和责任人，按影响处理修正或回退，复验前不进入完成状态。
- 批次完成：所有已选 PR 均完成该阶段要求的审查、集成验证和验收，或已获明确转期裁定；逐项回写账本、阶段进度、TODO 和 devlog。
- 最终发布及反馈站解决回复仍按原流程执行。“已合并”“已验收”“已发布”分别记录，不互相替代。

## 6. 账本模板

下列模板放入阶段 `PR_INTAKE.md`，每个 PR 一条。没有证据的字段写“待核实 / NOT RUN”，不要用空白暗示通过。

```markdown
# PR intake

- 收集时间 / 仓库 / 基线提交：
- 查询条件 / 分页完成情况 / 收集异常：
- 阶段 / 验收模式 / 范围裁定来源：

## PR #编号 — 标题

- 链接 / 作者 / GitHub 状态 / 是否草稿：
- 实际 base 分支 + SHA / head 分支 + SHA：
- 最终集成目标 / 目标版本（未确认写候选）：
- 关联 Issue / TODO / 批次 / 验收条件：
- 已实现范围 / 未实现设想 / 重复或替代关系：
- 父 PR / 子 PR / 依赖处理顺序：
- 主审 / 修正责任人：
- 范围决定（纳入 / 延期 / 不采纳）及依据：
- 流程状态 / 阻塞原因 / 下一步：
- 审查记录（时间、base/head、结论、问题）：
- 作者证据（仅自报，注明出处）：
- 主审验证 / CI / 用户验收（分别记录 SHA、环境、结果、证据）：
- 修正与复审记录（新 head、变更、失效证据、复验结果）：
- 实际合入时间 / 方式 / 目标提交：
- 合入后验证 / 发布版本 / 账本回写：
```

流程状态使用：`候选 → 已纳入 → 审查中 → 待合入 → 已合入待验证 → 已验收`。需要时转为 `待修正` 或 `等待依赖`，解决后返回审查；退出时用 `延期 / 不采纳 / 关闭未合并`。这些状态与 GitHub 的 open/closed/merged 分开记录，草稿不得直接进入待合入。

每次状态变化应有证据和下一步；“待合入”须满足当前阶段的合入前门禁，“已验收”须满足当前阶段的全部验收条件。

| 当前情况 | 谁推进、如何继续 | 何时退出当前状态 |
| --- | --- | --- |
| 候选、范围未定 | 主开发人员整理建议；版本负责人处理尚未决定的范围 | 有纳入、延期或不采纳结论及依据 |
| 已纳入、尚未审查 | 指定主审，检查依赖和审查材料 | 开始检查指定 base/head，转审查中 |
| 待修正 | 约定的修正责任人提交修正；主审接续复审 | 新提交与修正说明齐备，返回审查中；不是直接待合入 |
| 等待依赖 | 主开发人员跟踪前置项，登记阻塞条件 | 前置满足后重查 base/head、diff 与证据，返回审查 |
| 待合入 | 主开发人员按已有授权和分支规则集成 | 记录真实落入目标分支的提交，转已合入待验证 |
| 已合入待验证 | 主开发人员组织集成验证与本阶段验收 | 通过则已验收；失败保留未完成并关联修正项 |
| 延期、关闭或不采纳 | 主开发人员记录理由及任务去向 | 需要重启时重新核对范围和最新提交，不复用旧完成结论 |

PR 关闭未合并不等于需求取消：仍需将需求保留为待实现、关联替代 PR，或记录取消／转期裁定。只有被该 PR 覆盖的全部需求验收条件满足，才能完成对应 TODO；某个 PR 已验收也不能代替同一需求其余批次的验收。

## 7. 最小完成检查

- [ ] 三类输入已汇总；PR 扫描完整，候选与已排期范围分开。
- [ ] PR 已映射到任务和批次；依赖、重复实现、混合范围有处理结论。
- [ ] 每个拟合入 PR 的最新 base/head 均经过适用的审查和验证。
- [ ] 冲突、失败、缺失 CI、未验收项都有真实状态、责任人和下一步。
- [ ] 合入后已验证实际目标提交；TODO、阶段进度和 devlog 一致。

## 8. 修改后的使用效果示例

原流程以主开发人员承担实现为中心；这次补充的效果，是把其他人的已有实现接入同一版本循环。

| 情况 | 原流程未明确覆盖的部分 | 更新后的处理 |
| --- | --- | --- |
| Issue 对应的功能已有别人提交 PR | 计划可能仍然只安排主开发人员实现 | 同一 TODO 关联 PR，批次改为审查与集成 |
| PR 提交到另一个功能分支 | 仅看 develop 容易遗漏依赖贡献 | 全仓收集，按父子依赖排列批次 |
| 审查发现问题 | 修正责任、复审和进度难以接续 | 记录修正项、责任人、验证办法，修正后回到审查 |
| PR 已合并 | 容易把合并当作任务完成 | 先记已合入待验证，满足验收条件后才完成 TODO |

下面是**虚构的教学示例**，用于检查流程是否可执行，不代表真实 PR、入版决定或测试结果。假设本阶段已经批准“导出工作记录”与“改进导出提示”两个需求：

| 输入 | 去重后的任务 | 批次类型与依赖 | 下一步 |
| --- | --- | --- | --- |
| Issue DEMO-1：需要导出记录；PR DEMO-A 已有实现 | T1 导出工作记录 | b1：PR 审查与集成；无前置依赖 | 主开发人员核对导出内容和失败提示，检查测试证据 |
| 开发人员提议：改进导出提示；暂无 PR | T2 改进导出提示 | b2：自行开发；依赖 b1 的导出接口 | 沿原流程实施和验收 |
| PR DEMO-B：基于 DEMO-A 的额外格式支持；尚未排期 | 候选 C1 | 暂不生成当前版本实施批次 | 记录依赖 DEMO-A，等待范围决定 |

T1 在 TODO 中可写为：

```markdown
- [ ] T1 导出工作记录：通过 PR DEMO-A 的 b1 审查与集成完成。
  验收：导出内容与选中记录一致；失败时明确提示且不损坏原记录。
  主审：主开发人员；修正：PR 作者；详细状态与证据见 PR_INTAKE.md。
```

若审查发现导出失败时提示不清：b1 改为“待修正”，列出复现步骤和期望提示，范围内小问题由主开发人员直接修复，其他问题由约定责任人处理。收到新提交后复审相关差异；通过合入前要求才进入“待合入”。实际合入后先记“已合入待验证”，完成当前阶段要求的验证和验收后，T1 才打勾。b2 是否可开始仍遵守该阶段的依赖与验收模式。

评估这次 WIKI 更新，先看五件事：能否找到全部候选输入、能否避免重复开发、能否明确谁处理下一步、能否在修正后继续原批次、能否区分合并与验收。上述示例覆盖了这些判断路径；真实团队使用中的耗时、遗漏率和沟通次数改善尚未测量，不能仅凭文档完整就宣称协作效率已经提高。

版本交付核对：代码合入、用户验收、正式 Release/CLI 渠道、用户文档/devlog、反馈回写和计划归档分别留证。主开发者汇总实际提交、版本、资产、验证及遗留项；用户要求发布前确认时，完成可独立准备工作后提交具体材料，未获同意不执行发布。此检查复用既有 TODO/阶段/PR 账本，不另建审批体系。
