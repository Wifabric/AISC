# AISC 开发职责 v1.1

依据用户“按照你给出的分工往前推进吧”，将已讨论的分工接入开发手册。这里的 v1.1 是协作文档版本，不是产品版本。原有范围裁定、验收、发布批准及明确委托继续有效；具体人员在现有阶段计划中登记。

主开发人员操作见 [PR intake 工作流](pr-intake.md)；任务开发人员操作见 [贡献者工作流](contributor-workflow.md)。原始 [v0.1 讨论稿](development-responsibilities-draft.md)保留不改。

## 1. 基本分工

**主开发人员对整个版本的组织、技术一致性、集成质量与交付闭环负责；任务开发人员对自己承接任务的实现、验证、材料和返修负责。**

主开发人员可以亲自开发，也可以把实现、测试、文档、构建等具体工作交给其他人员；交出执行工作后，仍需确认版本层面的结果。其他开发人员参与完整任务周期，提交 PR 后仍需响应审查和约定的修正。

| 角色 | 负责什么 | 不应混淆的边界 |
| --- | --- | --- |
| 主开发人员（版本协调与集成负责人） | 汇总输入、组织方案和批次、协调依赖、组织审查、确认技术集成条件、统筹验证和发布收口 | 负责统筹不等于包办全部代码、测试或返修；不替代用户保留的决定权 |
| 任务开发人员（其他开发人员，也可由主开发人员兼任） | 承接范围明确的任务，准备方案、实现、自测、说明、PR，并处理约定的修正和交接 | 不因本地通过或 PR 合并就自行认定整个版本已验收或发布 |
| 用户／需求与验收负责人 | 按现有约定确认版本范围、范围变更、用户验收与例外、阶段收尾等 | 如同一人兼任主开发人员，仍区分技术结论和需求／验收决定 |
| AI 代理 | 在已有授权内协助对应角色收集、规划、开发、检查和记账 | AI 不是新增审批角色；原有明确委托继续有效，不因本稿重新申请授权 |

每个版本应明确主开发人员，每个任务明确执行人和主审；发布执行人可以另行指定。人员可以兼任，但记录中要看得出谁执行、谁作出结论。主开发人员自己的代码也应经过同样的检查；有人可独立审查时安排独立审查，只有自查时如实记录，不称为独立评审。

## 2. 完整任务清单与分工

“主开发人员负责”表示需要组织、确认和收口，具体动作可按任务委托。

| 开发环节 | 主开发人员负责 | 任务开发人员负责 | 交接产物／完成依据 |
| --- | --- | --- | --- |
| 1. 收集需求与贡献 | 汇总反馈 Issue、开发提议及全仓 PR，去重、识别缺口和依赖 | 提出问题、补复现材料，说明自己已有的实现和 PR | 关联来源的候选清单 |
| 2. 确定版本范围 | 提出优先级、取舍和版本建议，记录有权负责人的决定 | 说明工作量、风险、依赖和未明确的需求 | 确认后的 target；未入版项有去向 |
| 3. 总体方案与契约 | 协调架构、共享接口、数据格式、兼容和安全边界，处理跨任务冲突 | 为自己任务提出设计，说明影响，保持既定契约 | 方案／决策记录及可检验结果 |
| 4. 拆分 TODO 和批次 | 编排任务、负责人、依赖和审查安排，识别已有 PR 可复用的实现 | 确认承接边界、前置条件和可交付部分，反馈安排是否可行 | 有责任人与验收条件的批次条目 |
| 5. 环境与基线 | 统一集成基线、阶段模式和共用门禁，协调共享环境问题 | 在自己的分支搭建环境，确认依赖及使用的源码／产物版本 | 基线、环境、分支和阻塞说明 |
| 6. 编码与资源修改 | 协调共用文件和接口的改动；承担自己领取的任务 | 完成所承接的 UI、CLI、容器、依赖、测试、CI 或文档变更 | 与约定范围一致的代码和材料 |
| 7. 任务自测 | 明确适用门禁，检查证据是否充分，协调缺少的验证资源 | 跑任务相关验证及适用门禁，修复失败，明确 FAIL／NOT RUN | 绑定提交与环境的测试、构建和手测记录 |
| 8. 文档与交付材料 | 保持版本计划、状态和用户文档整体一致 | 更新本任务涉及的 README、接口说明、变更说明、手测步骤 | 与实现同步的文档和变更摘要 |
| 9. 提交 PR | 接收候选，将确认范围内的 PR 排入审查集成批次 | 提交清晰 PR，关联任务，说明范围、依赖、验证和未完成项 | 可审查的 diff 与交付说明 |
| 10. 审查与返修 | 组织审查，明确问题及复验要求，确认是否满足技术合入条件 | 回应问题、修正并补证据；提出异议时说明依据 | 问题逐项有结论，新提交经过复审 |
| 11. 冲突与集成 | 决定集成顺序，协调跨任务行为取舍，核实目标分支集成结果 | 更新自己的分支，处理与任务有关的冲突，重跑受影响验证 | 实际集成提交与验证结果 |
| 12. 批次及用户验收 | 汇总可验收成果、环境与限制，组织本阶段要求的验收并回写结论 | 提供可复现步骤和产物，配合定位、复验自己任务 | 用户结论、技术证据与未验收项分别记账 |
| 13. 版本整体回归 | 统筹跨批次、平台、安装／升级及高频链路验证，分派发现的问题 | 执行约定的回归部分，修复自己任务引入的问题 | 版本回归记录与剩余风险 |
| 14. 版本、打包与发布 | 统筹双轨版本、发布准备、候选提交、CI 与资产核验，沿用现有批准和委托规则 | 按任务准备发布说明、打包／安装验证或执行明确委托的发布步骤 | 对应实际提交的版本、产物和发布证据 |
| 15. 收尾与反馈闭环 | 核实完成／转期、归档计划、更新日志，统筹反馈站回复及既定清理 | 补任务最终记录、已知限制、后续事项，配合反馈回复 | 需求、批次、PR、版本之间可追溯 |
| 16. 发布后异常与改进 | 组织影响评估、修复或回退方案，按授权推进，回写经验与流程 | 提供诊断、修正、复验与交接，报告无法继续负责的事项 | 处理结论、责任交接及后续任务 |

## 3. 主开发人员需要持续把握的六件事

1. **版本要交付什么**：候选、已确认范围和转期项分清；新增范围由原有有权角色裁定。
2. **任务由谁做、按什么顺序做**：每个任务有人承接，依赖和公共接口冲突有处理办法。
3. **实现能否合在一起**：主审、集成顺序和跨任务行为一致，审查结论对应最新提交。
4. **证据是否足够**：贡献者自测、CI、集成回归和用户验收分别成立，不互相冒充。
5. **版本能否进入下一阶段**：按当前有效验收模式、既有授权及发布规则推进，不自行放宽要求。
6. **所有任务是否有结果**：完成、待修正、阻塞或转期都有明确记录，发布后的问题也有人接续。

这些责任不能因“交给别人写了”就消失；但不要求主开发人员亲自执行每项测试、修改每个冲突或替所有贡献者返修。

## 4. 据此划出的其他开发人员工作范围

其他开发人员可以承接任意边界明确的开发工作，包括功能、缺陷、测试、文档、CI、依赖维护和打包验证。分工依据是任务范围与能力，不固定为“主开发写后端、其他人写前端”。

每项承接工作的最小责任包包括：

- 弄清目标、范围、依赖和验收条件，先查已有任务与 PR，避免重复实现。
- 写出任务内方案，按基线建分支，完成实现和相关文档。
- 完成适用自测；无法验证的部分说明原因、影响与后续需要。
- 提交可审查的成果，配合复审、冲突解决及约定的集成验证。
- 回写任务结果；未完成或无法继续的工作显式交接，不能随 PR 提交自动结束责任。

以下事项先回到主开发人员协调：改动共享接口影响其他批次、扩大已确认任务范围、改变依赖或集成顺序、缺少会阻塞验收的环境、无法继续承接任务。若涉及用户保留的决定权，再由对应负责人裁定。任务范围内的普通实现选择由任务开发人员自行处理，不逐行请求许可。

## 5. 两类角色之间的交接

沿用 TODO、阶段计划及 PR_INTAKE 三层记录，下面的交接字段直接写在已有条目或 PR 中，不要求每次新建文档。

| 交接点 | 交出方提供什么 | 接收方做什么 |
| --- | --- | --- |
| 主开发人员 → 任务开发人员 | 任务编号、范围与不做项、基线、依赖、验收条件、已有决定 | 确认承接并补充方案；不清楚的事实先查，影响范围的选择再讨论 |
| 任务开发人员 → 主审 | PR、关联任务、已实现／缺口、base/head、验证证据、未测项、兼容影响 | 检查材料与依赖，进入审查；材料缺失时指出缺哪一项 |
| 主审 → 修正责任人 | 问题位置、触发步骤、期望结果、优先级、复验要求 | 修正或有依据地回应，给新提交及逐项处理说明 |
| 修正责任人 → 主审 | 新 head、修正说明、受影响验证和剩余事项 | 复审后明确待合入、继续修正或等待依赖 |
| 主开发人员 → 用户／验收负责人 | 对应构建、操作步骤、期望结果、已验证及未验证范围 | 按阶段规则给验收结论或明确例外 |
| 集成完成 → 任务收口 | 实际目标提交、集成和验收结果、后续事项 | 贡献者补任务记录；主开发人员核对 TODO、批次与 PR 状态一致 |

## 6. 贡献者流程入口

**查任务与现有 PR → 确认承接和范围 → 任务内方案 → 分支开发 → 自测与文档 → 提交 PR → 修正与复审 → 配合集成验收 → 记录完成或交接。**

有三种入口：

1. **领取已排期任务**：使用现成任务编号和批次，不重复生成版本计划。
2. **自行提出新需求**：先进入候选和范围讨论，确认后承接；未纳入时不承诺进入当前版本。
3. **已经有实现或 PR**：直接交付已有成果及范围说明，由主开发人员核对、关联任务、安排审查；不强迫重走一遍编码过程，也不因已经写好而自动入版。

提交 PR 后转入既有 [PR intake 工作流](pr-intake.md)。批次是否允许并行或进入下一批，遵守当前阶段已声明的模式；多人参与本身不取消已有验收条件。

## 7. 用一个任务检查职责是否闭合

虚构例子：本版本已确认“导出工作记录”需求。

1. 主开发人员把它排为 T1／b1，明确导出字段、失败行为、接口依赖及验收条件；开发人员乙确认承接。
2. 乙完成方案、实现、自测、说明和 PR。若实现需要改变其他任务使用的接口，先由主开发人员协调，不自行让其他批次适配。
3. 主开发人员组织审查，发现范围内的失败提示小问题时直接修复并复测；较大或跨契约问题再约定乙处理，记录实际修正者和新提交。
4. 主开发人员统筹集成与版本级影响验证，乙配合解决本任务问题；用户按有效阶段规则验收。
5. 乙补齐任务交付记录，主开发人员核对完成条件与版本计划，随后按既有流程安排发布和反馈闭环。

如果乙无法继续，主开发人员组织接手人；乙交出分支、已做／未做事项和复现方法。任务保持真实未完成状态。主开发人员可以接手，但这不是默认替全部贡献者收尾。

## 8. 执行约定与适用边界

本说明基于本地 [DEVELOP_WIKI](../../DEVELOP_WIKI.md) 的 §1（阶段、范围、验收）、§2／§3／§6（环境与实施）、§7／§8／§12（契约与安全）、§9（测试）、§10／§11（打包与发布）、§13（文档），以及现有阶段计划、PR 工作流整理。

已知本地手册包含历史发布描述，且与此前读取的远端 §1.4 验收模式不同。本说明只规定工作类别和责任，不据此重新制定发布命令、版本号或权限；实际执行以集成目标的有效规则和已有授权为准。

具体执行采用以下约定：

- 角色兼任与人员分派写入现有阶段计划；未明确的人选写“待安排”，不能替他人承诺任务已被接受。
- 主开发人员统筹集成和发布；实际操作可以明确委托他人。既有批准、权限和用户决定不因委托失效。
- 复用任务条目、PR 讨论或团队已有沟通渠道，在开始、提交、阻塞、修正及完成／转交时更新。影响依赖或验收的事项及时同步，不额外要求固定日报。
- 普通任务内的实现选择由任务开发人员处理；跨任务接口、范围变化、依赖变化、验收例外或交接回到相应负责人。已有决定直接引用，不重复确认。

小团队采用主开发人员统一 Preview：贡献者完成实现与必要测试后提交 PR，主开发人员整合、回归并提供统一候选验收。普通小修正直接修复，已有授权不重复申请；任务编号无需绑定开发者。仓库 [开发 Skill](../../skills/aisc-development/SKILL.md) 与本文同步。当前真实 PR 实践由单代理兼任角色，只有自查，真实多人协作效果与用户最终验收尚未完成。
