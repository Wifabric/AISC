## 怎样试用

在 `output/local-workflow-trial-20261105-165538/` 新建独立 Git 仓库，用三个 worktree 分别承载主开发人员、贡献者和审查者的工作副本。三个角色均由同一个代理顺序模拟，不是三个真实开发人员或独立评审者。

独立仓库没有 remote。所有提交、冲突和合并仅发生在这个训练仓库中，没有合并 AISC 的 develop、#62 或其他产品 PR。协作文档的输入副本保存在 `workflow-inputs/`。

本地用 `PR-DEMO-1.md` 作为交付单，记录任务、base/head、证据和状态，以模拟 PR 的信息交接。它不是 GitHub PR；远端 CI、分支保护和正式发布检查均未运行，也没有被当作通过。演练允许的是独立训练仓库技术操作，不构成放宽 AISC 的合入条件。

## 演练任务

T-DEMO-1 / b1：把选中的记录导出为 CSV。要求固定 `id,title` 两列、保持选中顺序、中文及逗号／引号／换行可正常往返、空列表仍有表头、无效输入不破坏已有目标文件。

任务范围、角色、验收和验证计划先写入 `lead/TASK.md` 并提交，再建立贡献者分支。初版实现有意使用不完整的 CSV 写法并缺少写入前校验，作为训练故障；下列失败不是新发现的 AISC 产品缺陷。

## 对流程文档的反馈

本次确认了三个交接行为可以实际执行：按具体问题退回修正；新 head 和新 base 出现后重新检查；技术合入后仍保持未完成的用户验收状态。

需要加强的地方是**验收覆盖对应关系**。首轮贡献者确实有两项通过的自测，但未覆盖整个任务。文档原有“提供验证证据”还可以更明确，因此已在[贡献者流程 §4–§5](../workflows/contributor-workflow.md)与[主审流程 §4](../workflows/pr-intake.md)补充：逐条将验收条件对应到结果和证据，未覆盖条件写 NOT RUN，不用通过总数替代覆盖判断。

该改进来自受控演练，不是对真实团队效率的统计结论。任务较小、故障预设、角色由同一代理模拟，都限制了本次验证强度。

## 原演练机器上的查看与复跑

本节所列 `output/` 目录、训练仓库及日志仅保存在原演练机器，未纳入此文档 PR。克隆仓库不会获得这些文件，以下命令只适用于保有该目录的机器；其他读者可依据本文任务与验收条件重新搭建演练。本记录是作者报告，不能替代主审对本次 PR 的验证。

演练目录包括：

- `lead/`：最终集成代码、任务和 Git 仓库。
- `contributor/`：贡献者分支及提交。
- `reviewer/`：最终审查提交的独立工作副本。
- `PR-DEMO-1.md`：从提交到返修、复审和集成的交付记录。
- `acceptance.py`：七项验收检查；`run_checks.py`：固定工作副本的运行入口。
- `sample.csv`：最终实现导出的合成样例；无需真实业务数据即可查看中文、逗号、引号和换行。

在 AISC 根目录运行以下命令，可对最终集成代码复跑七项检查（只会在演练证据目录写日志）：

```powershell
python output/local-workflow-trial-20261105-165538/run_checks.py output/local-workflow-trial-20261105-165538/lead user-rerun.log
```

可以直接阅读 TASK、交付单和测试日志理解效果，无需操作真实 GitHub PR。若要试角色交接是否容易理解，下一步由另一位实际使用者只按这几份材料接手，再记录不清楚或需要反复询问的位置。
